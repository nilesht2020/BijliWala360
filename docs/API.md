## 1. Conventions

### 1.1 Envelope
```jsonc
// 2xx
{ "success": true, "data": <T>, "meta": { "page": 1, "pageSize": 20, "total": 134 } }   // meta only on lists
// 4xx/5xx
{ "success": false, "error": { "code": "STATE_CONFLICT", "message": "Proposal is no longer pending approval.", "details": [] }, "requestId": "req_01J…" }
```

### 1.2 Headers
| Header | Use |
|---|---|
| `Authorization: Bearer <access JWT>` | Required on every non-public endpoint. |
| `Idempotency-Key: <uuid>` | **Required** on endpoints marked 🔁. Optional elsewhere. |
| `If-Match: <version>` | Optional optimistic lock on PATCH or PUT of versioned resources. On a mismatch the response is `409 VERSION_MISMATCH`. |
| `X-Request-Id` | Echoed back. Generated by the server if absent. |

### 1.3 Pagination, filtering, sorting
- Offset pagination: `?page=1&pageSize=20` (maximum 100). The response `meta` carries `{page, pageSize, total}`.
- Cursor pagination, for audit logs, notifications and ledger: `?cursor=<opaque>&limit=50`. The response `meta` carries `{nextCursor}`.
- Filters are named query parameters, for example `?status=OPEN&companyId=…&from=2026-11-01&to=2026-11-30`. Sorting: `?sort=-createdAt` (allow-listed fields only).

### 1.4 Data formats
- IDs are 24-character hexadecimal strings.
- Money is an integer number of **paise** (`amountPaise`).
- Dates are `YYYY-MM-DD`. Instants are ISO-8601 UTC.
- Shift times are `startMin` and `endMin` (0–1439).

### 1.5 Status codes
| Code | Meaning |
|---|---|
| 200 / 201 / 202 / 204 | OK, Created, Accepted (async), No Content |
| 400 `VALIDATION_FAILED` | Schema validation failed. `details[]` lists `{path, message}`. |
| 401 `UNAUTHENTICATED` / `TOKEN_EXPIRED` | Missing or invalid token. |
| 403 `FORBIDDEN` | Missing permission or wrong scope. |
| 404 `NOT_FOUND` | Not found, **or out of scope**. Out-of-scope resources return 404 so that their existence is not revealed. |
| 409 `STATE_CONFLICT` / `VERSION_MISMATCH` / `CONCURRENT_MODIFICATION` / `REQUEST_IN_PROGRESS` | Concurrency or state conflict. |
| 422 business rule codes | See §3. |
| 429 `RATE_LIMITED` | Includes a `Retry-After` header. |
| 500 `INTERNAL_ERROR` | Unexpected error. |

## 4. Endpoints

Legend: 🔓 public · 🔁 requires `Idempotency-Key` · ⓢ scope-restricted.

### 4.1 Auth
Every sign-in step returns `AuthStepResponse`: `AUTHENTICATED {accessToken, expiresIn, user}` | `SIGNUP_REQUIRED {signupToken}` | `MFA_REQUIRED {mfaToken}` | `MFA_ENROLLMENT_REQUIRED {mfaToken}`. Step tokens (signup and MFA) are short-lived JWTs with their own audience, so they are rejected as access tokens. On `AUTHENTICATED` the refresh token is set as the `sc_rt` cookie (`HttpOnly; SameSite=Strict; Path=/api/v1/auth`) and is never in the body.

| Method | Path | Permission | Description |
|---|---|---|---|
| POST | `/auth/otp/request` | 🔓 (10/h per IP, 5/15 min per mobile) | `{mobile}` → `{challengeId, expiresInSec, resendAfterSec}` |
| POST | `/auth/otp/verify` | 🔓 | `{challengeId, code}` → `AUTHENTICATED` for an existing user, otherwise `SIGNUP_REQUIRED`. Admin accounts are refused with `INVALID_CREDENTIALS`, because admins always need password + TOTP. |
| POST | `/auth/signup` | 🔓 | `{signupToken, name, userType: PROFESSIONAL/VENDOR/COMPANY, email?, acceptTerms: true}` → `AUTHENTICATED`. Professionals get the PROFESSIONAL role. Vendor and company admin roles are granted when the organisation is created (Phases 3–4). |
| POST | `/auth/admin/login` | 🔓 | `{email, password}` → `MFA_REQUIRED` or `MFA_ENROLLMENT_REQUIRED`. The account locks after `auth.maxFailedLogins` failures. |
| POST | `/auth/admin/mfa/enroll` | 🔓 (mfaToken) | `{mfaToken}` → `{secret, otpauthUrl}` |
| POST | `/auth/admin/mfa/enroll/confirm` | 🔓 (mfaToken) | `{mfaToken, totp}` → `AUTHENTICATED` |
| POST | `/auth/admin/mfa/verify` | 🔓 (mfaToken) | `{mfaToken, totp}` → `AUTHENTICATED`. Each code is accepted only once; replays fail. |
| POST | `/auth/password/login` | 🔓 | For company users who have set a password: `{email, password}` → `AUTHENTICATED` |
| POST | `/auth/password/forgot` | 🔓 | `{email}` → always 202, so the response never reveals whether an account exists |
| POST | `/auth/password/reset` | 🔓 | `{token, newPassword}`. Ends all sessions. |
| PUT | `/auth/password` | auth | `{currentPassword?, newPassword}` → `AUTHENTICATED`. Other sessions end. |
| POST | `/auth/refresh` | cookie | Rotates the refresh cookie → `{accessToken, expiresIn}`. Replaying a rotated token revokes the whole token family (`REFRESH_TOKEN_REUSED`). |
| POST | `/auth/logout` | cookie | Revokes the token family and clears the cookie |
| GET | `/auth/me` | auth | `SessionUser {id, name, userType, mobile?, email?, roleCodes, permissions, scopes, mfaEnabled}` |
| POST | `/admin/users/:id/sessions/revoke` | `session.revoke` | Force logout: revokes refresh sessions and invalidates live access tokens |

### 5.1 OTP login
```http
POST /api/v1/auth/otp/request
{ "mobile": "+919812345678", "purpose": "LOGIN" }
→ 200 { "success": true, "data": { "challengeId": "6743…", "resendAfterSec": 30, "expiresInSec": 300 } }

POST /api/v1/auth/otp/verify
{ "challengeId": "6743…", "code": "482913" }
→ 200 Set-Cookie: sc_rt=…; HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth
  { "success": true, "data": { "accessToken": "eyJ…", "expiresIn": 900, "user": { "id": "…", "userType": "PROFESSIONAL", "name": "…" } } }
```

### 5.2 Registration payment (online)
```http
POST /api/v1/registrations/me/payments/online
Idempotency-Key: 5b1e…
→ 201 { "data": { "paymentId": "674a…", "razorpay": { "keyId": "rzp_test_…", "orderId": "order_P…", "amount": 117994, "currency": "INR" } } }
# The amount is calculated on the server from the plan snapshot (fee + GST). The client never sends the amount.

POST /api/v1/registrations/me/payments/674a…/verify
{ "razorpay_order_id": "order_P…", "razorpay_payment_id": "pay_P…", "razorpay_signature": "…" }
→ 200 { "data": { "status": "PENDING_CONFIRMATION" } }   # becomes SUCCESS when the webhook arrives
```

### 5.3 Invitation response (vendor)
```http
PUT /api/v1/invitations/6750…/response
Idempotency-Key: 9c2f…
{ "decision": "INTERESTED", "fullPeriod": true, "offeredHeadcount": 3,
  "proposedWorkerIds": ["6711…", "6712…", "6713…"] }
→ 200 { "data": { "invitationId": "6750…", "status": "RESPONDED_INTERESTED", "responseVersion": 1,
        "availabilitySnapshot": { "checkedAt": "2026-11-13T10:02:11Z", "calendarOk": true, "conflicts": [] } } }
# Replaying the request with the same key returns an identical body. A different body with the same key returns 422 IDEMPOTENCY_KEY_REUSED.
# Changing the answer later with a new key appends responseVersion 2. If the invitation is locked by an approved proposal: 422 INVITATION_LOCKED.
```

### 5.4 Proposal submit and approve
```http
POST /api/v1/admin/jobs/6760…/allocation-proposals
{ "type": "STANDARD", "lines": [
   { "positionId": "6761…", "invitationId": "6750…", "workerId": "6711…" },
   { "positionId": "6761…", "invitationId": "6752…" } ] }

POST /api/v1/admin/allocation-proposals/6770…/warnings/ack   { "lineId": "L1", "codes": ["LOW_RATING"] }
POST /api/v1/admin/allocation-proposals/6770…/submit          Idempotency-Key: a1…
→ 200 { "data": { "status": "PENDING_APPROVAL", "version": 3 } }
```
